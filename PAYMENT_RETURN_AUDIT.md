# Post-Xendit return audit

Scope: return verification only. No modal, payment creation, webhook, database, or deployment changes.

## Findings and required report

1. **Return URL passed to Xendit in checked-in code:** `create-cart-xendit-payment` serializes `sessionPayload` directly into the POST to `https://api.xendit.co/sessions`. Guest success is `${appOrigin}/cart?payment=success`; authenticated success is `${appOrigin}/my-orders?payment=success&order=${encodeURIComponent(order.id)}`. Cancellation uses `payment=cancelled` on the corresponding route. `appOrigin` is `new URL(SWEET_BAKES_APP_URL).origin`, validated as HTTPS. The deployed environment value was not accessible. The hardcoded CORS origin `https://sweetbakes-ten.vercel.app` is not proof of that environment value.

2. **Actual failed-session landing URL:** not available. A read-only HTTP request to `https://sweetbakes-ten.vercel.app/cart?payment=success` returned HTTP 200 at that exact URL. This was not a replay of the customer's Xendit session.

3. **Presence of `payment=success`:** confirmed for the direct HTTP request, unknown for the failed payment session. Cart reads `new URLSearchParams(window.location.search).get('payment')`. It polls only when the value is exactly `success`, the customer-authenticated prop is false, and parsed return context has an order ID and guest email. The generated cancellation value is `cancelled`; `cancel` and `failure` are not generated by this source and do not start success polling.

4. **Context after the failed return:** unknown because no browser is connected. Development diagnostics now identify absent context and authentication-related early exits without logging email values.

5. **Storage consistency:** both writer and reader use `window.localStorage` and `sweetbakes:cart-payment-return-v1`. Neither uses sessionStorage for this flow. Guest payload is `{ orderId, guestEmail }`; authenticated payload is `{ orderId }`. No key or response-field mismatch was found in source.

6. **Survival across redirect:** the writer executes immediately before `window.location.assign(paymentData.paymentUrl)`. It now reads back the exact saved value and throws before navigation if retention fails. This verifies local retention, not cross-origin availability. Localhost, preview, production, and different hostnames have independent storage. Whether the failed checkout crossed origins remains unknown. Previously, both handlers deleted context on timeout; Cart also removed the return query, and My Orders removed it when checking started. Pending/timeout state now retains context and URL for refresh recovery. Verified success or explicit cancellation still consumes transient return state.

7. **Guest status-only payload:** `supabase.functions.invoke('create-cart-xendit-payment', { body: { orderId: receipt.orderId, guestEmail: receipt.guestEmail, statusOnly: true } })`. The identifier is the stored database order ID, not the cart or redirect parameter.

8. **Status-only response contract in source:** `{ orderId: order.id, orderNumber: order.order_number, customerId: order.customer_id, paymentStatus }`, where `paymentStatus` is the lowercased canonical `orders.payment_status`. Frontend reads `data.paymentStatus` and accepts `paid`, `verified`, or `payment_verified`. HTTP success is not payment success. The actual failed-session response is unavailable. Guest authorization checks email, NULL ownership, and a 24-hour creation window. After paid status, the existing `track_guest_order` RPC must also return the matching order number, verified payment status, and nonempty items before the cart clears. Diagnostics now distinguish this second-stage failure from an unpaid status response.

9. **Failed test order database values:** unavailable. No test order ID was supplied and there is no connected Supabase admin tool. No order was read or modified through privileged access.

10. **Webhook update and timing:** unverified for the failed order. Checked-in webhook code writes `payment_status: 'paid'` after its existing validation. Source alone cannot establish webhook arrival or update latency. Eight verification attempts, with seven 1.5-second gaps plus request time, remain unchanged. No evidence justified extending that window.

11. **Root cause:** production incident root cause is not established. A definite recovery defect was found and fixed: an unresolved timeout destroyed the context required to verify the same order after a delayed backend update. Mocked control-flow tests reproduce timeout and confirm successful refresh recovery. This does not prove timeout caused the reported incident. The unchanged cart and absent modal can also occur after a paid status response if canonical detail loading fails.

12. **Files changed:** `src/cartpage/CartPage.jsx`, `src/cartpage/paymentConfirmation.js`, `src/cartpage/paymentConfirmation.test.js`, `src/cartpage/paymentReturnFlow.test.js`, `src/myorders/MyOrdersPage.jsx`, and this report. Requested development-only events are present: context saved, detected success URL, verification started, verification result, verification timeout. Logged fields exclude email values, order objects, tokens, credentials, and provider payloads.

13. **Edge Function deployment:** not required for these changes. No Edge Function source was modified.

14. **Frontend deployment:** required to publish these changes; not performed. No migrations are required or applied. Diagnostics intentionally run only in development builds, not the production Vercel build.

15. **Validation:** production build passed (existing large-chunk warning); ESLint passed for changed JavaScript/JSX/test files; `git diff --check` passed; 35 Node tests passed. New tests execute the actual guest return effects using a deterministic clock and mocked network, covering detection, request payload, delayed paid status, canonical details before clear/modal state, cancellation, missing context, and timeout/refresh recovery. Storage tests cover minimum payload and failed writes. These are not live browser or Xendit tests; visual interaction, actual payment completion, and live webhook timing remain untested.

## Evidence still needed

The failed test order ID/order number, exact URL immediately after Xendit returns, and read-only Supabase order status/webhook logs are needed to finish the production diagnosis. No speculative URL, response-contract, or webhook change was made in their absence.
